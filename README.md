# Chat Backend

Node.js + TypeScript chat API. PostgreSQL (through Prisma) stores users, direct/group chats, and chat membership; Firebase Firestore stores messages, per-user read receipts, and last-seen message pointers.

## Requirements

- Node.js 20+
- PostgreSQL
- A Firebase project with Firestore enabled
- Firebase service-account credentials or Application Default Credentials

## Setup

1. Install dependencies with `npm install`.
2. Copy `.env.example` to `.env` and set `DATABASE_URL`.
3. Configure `FIREBASE_SERVICE_ACCOUNT_JSON` with the service-account JSON on one line, or configure Application Default Credentials. Set `FIREBASE_PROJECT_ID` if it is not inferred from credentials.
4. Run `npm run db:migrate -- --name init` to create the relational schema. Existing installations should run `npm run db:migrate -- --name group-chat-bonus` to apply the group-membership migration and preserve current direct-chat members.
5. Add users to the `User` table before creating chats. User creation/authentication is intentionally outside this API's requested scope.
6. Run `npm run dev`, or build and run with `npm run build` and `npm start`.

## API

- `POST /chat/create` — body: `{ "userAId": "...", "userBId": "..." }`; returns `{ "chatId": "..." }`. Repeated calls for the same pair return the same chat.
- `POST /chat/:chatId/message/send` — body: `{ "senderId": "...", "text": "..." }`.
- `GET /chat/:chatId/messages?limit=50` — returns messages in ascending timestamp order; `limit` defaults to 50 and is between 1 and 100. An optional `userId` query parameter can be supplied to verify chat membership.
- `POST /chat/:chatId/message/:messageId/read` — body: `{ "userId": "..." }`; writes a receipt to `chats/{chatId}/messages/{messageId}/readReceipts/{userId}`.
- `POST /chat/:chatId/lastseen` — body: `{ "userId": "...", "messageId": "..." }`; updates `chats/{chatId}/lastSeen/{userId}`.
- `GET /user/:userId/chats` — returns each chat's ID, member IDs, and timestamps.
- `POST /chat/group/create` — body: `{ "creatorId": "...", "memberIds": ["...", "..."], "name": "Optional group name" }`; creates a group with at least three distinct users and makes the creator an admin.
- `POST /chat/:chatId/members` — body: `{ "actorId": "admin-user-id", "userId": "user-to-add" }`; an admin adds a user.
- `POST /chat/:chatId/admins` — body: `{ "actorId": "admin-user-id", "userId": "member-to-promote" }`; an admin promotes a group member.
- `DELETE /chat/:chatId/members/:userId` — body: `{ "actorId": "admin-user-id" }`; an admin removes a member. The last admin cannot be removed until another member is promoted.
- `PATCH /chat/:chatId/message/:messageId` — body: `{ "userId": "sender-id", "text": "Updated text" }`; only the original sender may edit a message.
- `DELETE /chat/:chatId/message/:messageId` — body: `{ "userId": "sender-id" }`; only the original sender may delete a message.
- `GET /health` — liveness check.

Firestore messages live at `chats/{chatId}/messages/{messageId}`. Chat membership is checked on send, read-receipt, and last-seen operations. The message-list endpoint accepts the task's `?limit=50` form; supply optional `userId` when the caller should be checked against membership. Message text is limited to 5,000 characters. Message deletion is a soft delete in Firestore so existing receipts and ordering remain intact.

## Notes

- Chat IDs use UUIDs and are generated by Prisma.
- User records must already exist in PostgreSQL; this service does not expose user provisioning or authentication.
- Direct chats use normalized participant IDs to ensure repeat create requests return the same chat. Group membership and admin roles are stored relationally.
- This task's API uses caller-supplied IDs and does not implement authentication. Do not expose it publicly until authentication is added and each caller's identity is derived from a verified token.
